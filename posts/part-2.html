A real interface into inference infrastructure for app teams

September 2026. Part 2 of Building an LLM inference platform. Code: tag post-2.

Part 1 set up pinned tooling, a disposable kind cluster and a mock engine that behaves like vLLM at its edges. This part adds the Helm chart that puts a model into service, and the tests that show it behaves the way the chart says it does.

What this part covers

The people who want a model served usually don't want to learn how the engine underneath it is run, and I don't think they should have to. Their interface into the system is a Helm chart: they fill in a short values file (which image, which model, how long it takes to load) and the chart turns that into a running service. This post goes through what is in that values file and why, the health checks, and how I set up rolling updates and node drains so that in-flight requests finish instead of being cut off. There are two kinds of test for all of this, unit tests for the templates that run in a second with no k8s cluster, and load tests that run inside of a cluster. I also added CI along the way (ADR 0006). It runs the same just check recipe I run on my laptop, using the same Nix flake, so the tool versions are pinned in one place and nowhere else.

The values interface

charts/inference-service deploys one model per Helm release (ADR 0007), so if I want to serve three models I install the chart three times, each with its own values file. I originally looked at two other ways of doing it. The first was one chart that takes a list of models, but then all of the models go out in the same release, and one bad model holds up the rest of them. The second was to write an operator (a controller that runs in the cluster and watches a Model custom resource), which is a lot more to build and run than I need for this series. An operator makes sense when something has to react to what's happening in the cluster, like scaling a model to zero when nobody's using it. My models are just config that doesn't change until I commit a new values file, and Argo CD already applies whatever is in Git, so an operator wouldn't have anything to do.. In this example with the architecture I've chosen, having lots of small releases, each with its own values file, is also just the kind of thing Argo CD is good at managing. I'll write about this more in part 4.

The values file has two required fields, image.repository and image.digest (the sha256 hash of the image contents). image.tag is refused, because a tag can be moved to point at a different image later and a digest can't, so what gets deployed is always the exact image that was tested. model.name, engine.args and engine.env say what the engine is and how it starts. Those are the only values that are different between the mock and vLLM, and the templates don't have any mock-specific branches in them. Locally just deploy runs this: 

helm upgrade --install "mock" "charts/inference-service" \
    --set image.repository="localhost:5001/mock-engine" \
    --set image.digest="$(cat local/mock-engine.digest)" \
    --set-string engine.env.STARTUP_DELAY_SECONDS=15 \
    --wait --timeout 3m

The chart checks the values at install time, in two places. Most of it is done by values.schema.json (a JSON Schema file that Helm validates the values against before it renders anything). The image helper in _helpers.tpl covers what the schema can't say clearly, and fails with its own message, like the first error here. This is what it looks like when values are rejected:

Probes sized for weight loading

In part 1 I ran the mock with kubectl run and no probes (the health checks Kubernetes makes against a container), so the pod was marked Ready straight away, and it answered 503 four times before the engine was actually up. With a real engine that gap is as long as the weights take to load, and any traffic sent to the pod in that time fails.

The chart covers that gap with a startup probe, which is a check that has to pass once before Kubernetes treats the container as started. engine.loadTimeoutSeconds (default 600) is how long the engine is allowed to take to load. The chart divides it by probes.periodSeconds and rounds up to get the startup probe's failureThreshold, so with the defaults that is 600 / 5 = 120 attempts. The readiness probe (which decides if the pod gets traffic) and the liveness probe (which decides if the container gets restarted) don't run until the startup probe has passed once. I set the liveness threshold to 6 failed checks in a row, which is generous on purpose, since restarting a loaded engine drops every request it is holding. This is what renders with the defaults: 

          startupProbe:
            httpGet:
              path: /health
              port: http
            periodSeconds: 5
            timeoutSeconds: 2
            failureThreshold: 120
          readinessProbe:
            httpGet:
              path: /health
              port: http
            periodSeconds: 5
            timeoutSeconds: 2
            failureThreshold: 3
          livenessProbe:
            httpGet:
              path: /health
              port: http
            periodSeconds: 5
            timeoutSeconds: 2
            failureThreshold: 6
          lifecycle:
            preStop:
              sleep:
                seconds: 10

Rollouts that keep streams alive

A streamed response can run for a long time, and if a rollout stops a pod as soon as its replacement is Ready, any stream that pod was in the middle of gets cut off. The chart handles this in two ways. The Deployment uses maxUnavailable: 0 and maxSurge: 1, which means a rollout adds one new pod at a time, and a serving pod is only removed after its replacement has passed its probes. Then when a pod is removed, it first gets a preStop hook (something Kubernetes runs in the container before it sends SIGTERM) that sleeps for 10 seconds. The pod keeps serving during the sleep, which gives the endpoints controller time to take it out of the Service so that no new requests are sent to it. After that it has what is left of the 90 second termination grace period (the 90 seconds includes the sleep) to finish the streams it still has open. For the sleep I used the sleep lifecycle action that is built into Kubernetes, instead of an exec that runs a sleep command inside the image. That needs Kubernetes 1.30, which is why Chart.yaml says kubeVersion: ">=1.30.0-0".

When replicaCount is more than 1, the chart also renders a PodDisruptionBudget with minAvailable: 1. That is a rule that tells Kubernetes how many pods of the release have to stay up during a voluntary disruption like a node drain (emptying a node of its pods, usually before maintenance), so a drain has to wait for a replacement before it can evict the last serving pod. The unit test for it has two cases. With one replica no PodDisruptionBudget is rendered, and with three replicas one is rendered with minAvailable: 1.

CI is two GitHub Actions jobs. The first installs Nix and runs nix develop .#ci -c just check, which runs the formatters in check mode (they report a file that needs formatting and don't change it), the linters, and the chart checks above. The second builds the mock image with Docker, starts it, and checks that /health gets to 200 and that /metrics has the vLLM series names in it. Neither job runs a cluster. There is also just hooks, which installs a git pre-commit hook that runs the linters on just the files that are staged. I wrote it with plain git and just instead of using the pre-commit framework, because the framework would be a second place that pins tool versions, and I want those pinned in the flake only.

A rollout under load

The unit tests show that the manifests say the right thing, but they can't show that Kubernetes does the right thing with them. For that I need traffic running while pods are being replaced, and a count of what happened to every request (ADR 0008).

loadtest/load.py does that. It runs as a pod inside the cluster and sends its requests to the release's Service name. It runs four loops of streaming chat completions for a fixed length of time, and counts every request by how it ended: ok if the stream got to [DONE], truncated if it ended early, http_<code> for an error status, or the name of the exception class if the connection failed. If it counted anything other than ok it exits with a failure mode of 1. It only uses the Python standard library, so it can run in the mock engine's image, which is already in the registry and has Python in it, and I didn't have to pin another image.

The first thing I tried was running the load from my laptop through kubectl port-forward. That doesn't work for this, because port-forward picks one pod when it connects and stays on that pod, it doesn't follow the Service through a rollout. So it reports failures that a client going through the Service would never have seen.

just rollout-test starts the load pod, waits 20 seconds, then does a helm upgrade with a changed env value so that every pod gets replaced. It waits for the rollout to finish and prints the counts:

loadtest/load.py 
"""
Streaming load generator. Runs as a pod inside the cluster, against a
release's Service, so a rollout or a node drain that drops requests shows up
as a number rather than a feeling.

Every request is counted by outcome:
  ok          stream reached data: [DONE]
  truncated   HTTP 200 but the stream ended early (pod stopped mid-response)
  http_<code> non-2xx response
  <ExcName>   connection-level failure (refused, reset, timeout)

Configured by environment:
  TARGET              base URL, e.g. http://mock-inference-service:8000
  DURATION_SECONDS    how long to run
  CONCURRENCY         parallel request loops
  MODEL_NAME          model id to send

Stdlib only, so it runs unchanged in the mock engine's image. Each request
opens a new connection, which is the simplest client and also the most
forgiving one; a keep-alive client can see one reset per retired pod.
"""

import collections
import json
import os
import sys
import threading
import time
import urllib.error
import urllib.request

URL = os.environ.get("TARGET", "http://mock-inference-service:8000") + "/v1/chat/completions"
DURATION = float(os.environ.get("DURATION_SECONDS", "120"))
CONCURRENCY = int(os.environ.get("CONCURRENCY", "4"))
MODEL = os.environ.get("MODEL_NAME", "mock/mock-8b")

BODY = json.dumps(
    {
        "model": MODEL,
        "stream": True,
        "max_tokens": 20,
        "messages": [{"role": "user", "content": "hi"}],
    }
).encode()

counts: collections.Counter[str] = collections.Counter()
lock = threading.Lock()
started = time.monotonic()
deadline = started + DURATION


def one_request() -> str:
    req = urllib.request.Request(URL, data=BODY, headers={"content-type": "application/json"})
    try:
        with urllib.request.urlopen(req, timeout=30) as resp:
            done = False
            for line in resp:
                if line.startswith(b"data: [DONE]"):
                    done = True
            return "ok" if done else "truncated"
    except urllib.error.HTTPError as e:
        return f"http_{e.code}"
    except Exception as e:  # noqa: BLE001 - every failure kind is a count, not a crash
        return type(e).__name__


def worker() -> None:
    while time.monotonic() < deadline:
        outcome = one_request()
        with lock:
            counts[outcome] += 1


threads = [threading.Thread(target=worker, daemon=True) for _ in range(CONCURRENCY)]
for t in threads:
    t.start()

print(f"load: {CONCURRENCY} streams against {URL} for {int(DURATION)}s", flush=True)
while any(t.is_alive() for t in threads):
    time.sleep(5)
    with lock:
        snapshot = dict(counts)
    print(
        f"t={int(time.monotonic() - started):4d}s total={sum(snapshot.values()):5d} {snapshot}",
        flush=True,
    )

with lock:
    final = dict(counts)
failures = {k: v for k, v in final.items() if k != "ok"}
print(
    f"final total={sum(final.values())} ok={final.get('ok', 0)} failures={failures or 'none'}",
    flush=True,
)
sys.exit(1 if failures else 0)

# run loadtest/load.py as a pod against a release's Service; pin it to a node with node=
load release="mock" seconds="120" concurrency="4" node="":
    #!/usr/bin/env bash
    set -euo pipefail
    img="{{ mock_image }}@$(cat local/mock-engine.digest)"
    node="{{ node }}"
    overrides='{}'
    [ -z "$node" ] || overrides="{\"spec\":{\"nodeName\":\"$node\"}}"
    kubectl delete pod load --ignore-not-found --wait >/dev/null
    kubectl run load --restart=Never --image="$img" --overrides="$overrides" \
        --env TARGET="http://{{ release }}-inference-service:8000" \
        --env DURATION_SECONDS="{{ seconds }}" --env CONCURRENCY="{{ concurrency }}" \
        --command -- python -c "$(cat loadtest/load.py)"

# wait for the load pod to finish and print its counts; exit 1 if any request failed
_load-result:
    #!/usr/bin/env bash
    set -euo pipefail
    # not `kubectl wait`: it never returns for a pod that ends in Failed
    phase=""
    for _ in $(seq 1 120); do
        phase=$(kubectl get pod load -o jsonpath='{.status.phase}')
        case "$phase" in Succeeded|Failed) break ;; esac
        sleep 5
    done
    ok=0; [ "$phase" = Succeeded ] && ok=1
    kubectl logs load
    kubectl delete pod load >/dev/null
    [ "$ok" = 1 ]

# replace every pod of a release while load runs; the final line of the load log is the verdict
rollout-test release="mock":
    #!/usr/bin/env bash
    set -euo pipefail
    just load "{{ release }}" 150 4
    sleep 20
    echo "--- helm upgrade: a changed env value forces every pod to be replaced"
    helm upgrade "{{ release }}" "{{ chart }}" --reuse-values \
        --set-string engine.env.ROLLOUT_MARKER="$(date +%s)" >/dev/null
    kubectl rollout status deploy/"{{ release }}-inference-service" --timeout=5m
    just _load-result

# drain the node running the release's first pod while 2 replicas serve under load
drain-test release="mock":
    #!/usr/bin/env bash
    set -euo pipefail
    helm upgrade "{{ release }}" "{{ chart }}" --reuse-values --set replicaCount=2 \
        --wait --timeout 3m >/dev/null
    sel="app.kubernetes.io/instance={{ release }}"
    echo "--- before"
    kubectl get pods -l "$sel" -o wide
    node=$(kubectl get pods -l "$sel" -o jsonpath='{.items[0].spec.nodeName}')
    other=$(kubectl get nodes -l '!node-role.kubernetes.io/control-plane' -o name | grep -vx "node/$node" | head -1 | cut -d/ -f2)
    just load "{{ release }}" 150 4 "$other"
    sleep 20
    echo "--- kubectl drain $node"
    kubectl drain "$node" --ignore-daemonsets --delete-emptydir-data --timeout=4m
    echo "--- after"
    kubectl get pods -l "$sel" -o wide
    kubectl uncordon "$node" >/dev/null
    kubectl get pdb -l "$sel"
    just _load-result

What these tests can't tell you

The load client opens a new connection for every request, which is the most forgiving way a client can behave here. A keep-alive client (one that reuses a connection across requests) can see one connection reset for each pod that is retired, and I left measuring that for the benchmark work. Latency isn't measured at all, since the mock's timings are just numbers I set in environment variables.

The drain defaults are sized for the mock. I don't know yet if 90 seconds is enough for vLLM to finish a long streamed response, that is a question for part 5, and the rollout test is there so that I can answer it by running it instead of guessing. Both tests need a cluster, so for now they only run on my laptop, until CI has a cluster of its own.

The startup probe is also only half of the weight loading story. It stops traffic reaching a pod that isn't ready, but it doesn't make the pod ready any sooner, and with the mock there is nothing to load, so loadTimeoutSeconds is a budget I have never actually spent. With vLLM every new pod would download the weights from Hugging Face before it can serve, which makes a rollout take as long as the download and makes the pod depend on a network it shouldn't need. The fix is to stage the weights before the pod starts, on a volume that outlives the pod or in an OCI image that is pulled by digest like the engine image is, so that a model is pinned by revision and checksum the same way the image is. That needs real weights to mean anything, so it goes in part 5 with vLLM, and the chart will grow a model.source value then.
